Minimal Browser — Full Rewrite Goal Plan

23 August 2026 · Author: Puvaan · Baseline: b04b346 on main

Goal: replace Electron, React, Node-side browser orchestration, persistence, packaging, and the landing-page release path with a shared Rust core plus thin native AppKit and Win32 shells using WKWebView and WebView2, while preserving current behavior and proving a decisive performance win before cutover.

Apple provides a truly nonpersistent WKWebsiteDataStore. Microsoft documents that WebView2 browsing data lives in a user-data folder whose lifetime the host controls; the Windows adapter therefore needs explicit runtime cleanup rather than claiming in-memory parity. Microsoft also recommends lightweight XAML or Win32 instead of WebView2 for initial UI because creating WebView2 adds startup cost, which is why the final shell is native.

3. Non-negotiable security boundaries

  • Remote page webviews receive no native command bridge, host objects, filesystem access, secret access, or initialization scripts that expose privileged APIs.
  • Only native shell code can invoke the allowlisted Rust core API. Every command validates arguments and lifecycle state.
  • Permissions default to deny. Camera, microphone, location, notifications, downloads, external schemes, and popups require explicit policy.
  • TOTP secrets use OS-backed secret storage. Logs, telemetry, agent snapshots, crash reports, and benchmark artifacts never contain secrets or page credentials.
  • Windows temporary WebView2 data is cleared while controls are alive, all webviews are closed, and only the validated per-session directory is removed afterward.
  • Performance work may not disable sandboxing, web isolation, code signing, CSP, or permission checks.

5. Firefox authenticator migration contract

The rewrite is not feature-complete until Puvaan can export the Authenticator extension vault from Firefox, import it locally into Minimal, verify every supported account, and retain a recovery backup without exposing secrets.
  1. Provide a dedicated Import from Firefox Authenticator wizard. Document the source workflow as Firefox Authenticator → Settings → Backup → Download Backup File.
  2. Accept the extension's standardized unencrypted authenticator.txt, unencrypted JSON/OTPStorage, one-URI-per-line otpauth://, and password-protected authenticator.json formats. Detect the format and version rather than guessing.
  3. For encrypted backups, request the password in a native secure field and decrypt locally only. Support current version 8+ fixtures and separately tested legacy ≤7 fixtures; show the upstream weak-KDF warning for old backups without weakening validation.
  4. Preserve issuer, label/account, secret, algorithm, digit count, period, counter, ordering, and supported icon metadata. Implement every account type found in the source vault—including TOTP, HOTP, Steam, and Blizzard/Battle.net—or block finalization with an explicit account-by-account unsupported report. Never silently skip.
  5. Preview totals before writing: importable, duplicate, invalid, password-protected, and unsupported. Show no secret values in the preview, logs, crash reports, analytics, agent output, or accessibility labels.
  6. Deduplicate by normalized credential identity while retaining distinct accounts that share an issuer or label. Resolve conflicts explicitly.
  7. Write the complete import transaction to Keychain/Credential Manager atomically. On any failure, roll back every newly written item and leave the source backup untouched.
  8. After import, generate current codes and provide a manual verification checklist before marking migration complete. Do not delete or modify Firefox data.
  9. Offer a password-protected Minimal recovery export and a standards-based interoperable export. Never create an unencrypted backup without an explicit warning and confirmation.
  10. Test with sanitized upstream-format fixtures for Firefox Authenticator current and legacy encrypted/unencrypted formats, malformed files, wrong passwords, duplicates, large vaults, and every supported OTP type.

The existing code only supports unencrypted JSON and otpauth:// lines and currently skips encrypted, HOTP, Steam, and Blizzard/Battle.net entries. The rewrite must close those gaps rather than porting the current limitation.

The Authenticator extension's official guide documents local unencrypted and password-protected backup downloads. Its maintainers identify the conventional filenames as authenticator.txt and authenticator.json. Versions 8+ changed encryption after a disclosed weak-KDF issue in versions ≤7, so current and legacy encrypted fixtures require separate handling.

7. Windows-specific acceptance contract

  • Build and smoke-test on a native Windows runner, not WSL2 alone.
  • Ship x64 NSIS and portable artifacts with stable names; add ARM64 only as a separately verified target.
  • Ensure WebView2 Evergreen is present or bootstrap it through the installer; fail with a useful message if runtime creation fails.
  • Use one shared per-session WebView2 environment/UDF to avoid extra browser processes; never reuse it across launches when fresh-session mode is active.
  • Verify Control-based shortcuts, hidden/custom title bar, DPI scaling, multiple monitors, installer directory choice, Start menu/desktop shortcuts, downloads, file dialogs, and uninstall cleanup.
  • Add a Windows release workflow; the merged PR added packaging configuration but no Windows release job.
  • Fix the repository permission or token path that currently prevents Release Please from creating its release PR.
  • Do not publish “Windows available” on the site until a downloadable artifact and clean-machine smoke test exist.
  • Keep signing as an explicit production blocker until a certificate and secret-backed CI flow exist.

8. Rewrite operating rules

  • This is a full rewrite, but not a blind big-bang deletion. Build new vertical slices beside the legacy baseline, then delete legacy only after cutover gates pass.
  • Do not silently drop or redesign current features. Record intentional changes in an architecture decision log.
  • Do not optimize from intuition. Every optimization needs a trace or benchmark and a before/after artifact.
  • Keep commits phase-scoped, conventional, and independently reviewable. Never mix generated build outputs or secrets.
  • At every phase, update the parity matrix, benchmark delta, risks, and next unblocker.
  • If either native platform adapter cannot meet security, lifecycle, accessibility, or performance requirements, stop and present evidence before switching stacks.
