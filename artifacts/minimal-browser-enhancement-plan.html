Minimal Browser — Performance and Product Enhancement Plan

23 August 2026 · Author: Puvaan · Context: mini-browser v0.1.0

Recommendation: optimize and instrument the current Electron/WebContentsView core first. Do not rewrite the rendering engine now. Run a bounded Swift/WKWebView experiment only after the optimized Electron baseline exists, and keep it only if it wins decisively on startup, memory, and energy without unacceptable compatibility loss.

1. What “fastest browser” should mean

A universal “fastest browser” claim is not defensible: browser speed has several independent dimensions, and synthetic scores change with hardware, browser versions, settings, and benchmark versions. Minimal should pursue a precise promise:

  • Fastest path from launch to useful browsing among the tested macOS browsers.
  • Lowest shell overhead above the embedded engine.
  • Competitive page-engine scores with the matching Chromium generation.
  • Lower default page cost from blocking unnecessary requests.
  • Bounded tab memory and background energy under realistic workloads.

The website should say “fast in our test” or name the winning metric until Minimal has repeatable, same-machine evidence for anything broader.

3. The first performance fixes

PriorityChangeWhyAcceptance evidence
P0 Replace the per-request full suffix scan with host-label Set.has lookups. hostIsBlocked currently walks up to ~96k entries for every request. 100k-rule benchmark: median under 10 µs; exact-match and parent-suffix tests pass.
P0 Add a 24-hour freshness policy, ETag/Last-Modified requests, schema version, and worker-thread parsing for EasyList caches. Every new app session currently fetches, parses, deduplicates, and rewrites both lists. Fresh cache performs no network refresh; first navigation never waits for parsing; durations exported.
P0 Add performance marks and JSON export for process start, app ready, shell visible, omnibox usable, session ready, view creation, navigation commit, FCP, LCP, and load. The current roadmap has prose goals but no reproducible measurements. One command creates raw samples plus machine, OS, browser, engine, commit, rule-count, and cache metadata.
P1 Choose one state-delivery model, add revisions, suppress unchanged snapshots, and coalesce page metadata events. Commands both return full state and trigger a full pushed state; navigation triggers more full updates. No duplicate revision reaches the renderer; tab-switch latency improves or remains neutral.
P1 Batch layout IPC with requestAnimationFrame, skip identical bounds, and address the active view directly. ResizeObserver and window resize can both send immediate layout updates, followed by a scan of every tab. At most one bounds update per frame; no update for identical rounded geometry.
P1 Remove the unused tooltip provider and measure removing the guest MV3 authenticator extension. The shell renders no tooltip component, and the extension popup is not exposed by Electron’s chrome. Compressed entry falls without behavior loss; extension removal is kept only if memory/process count improves.
P1 Freeze, then discard eligible background tabs under pressure. Every navigated tab stays live until closed. 10/20-tab private memory drops ≥25% versus optimized baseline; audible, form-dirty, download, WebRTC, and agent tabs are exempt.

Keep the existing security boundaries: sandboxed page contents, context isolation, no Node integration, shared ephemeral guest session, and lazy creation of page views.

Record exact versions on every run; Minimal is presently one Chromium milestone behind local Chrome.

Protocol

  1. Use one plugged-in Mac, Low Power Mode off, fixed 60 Hz, identical fullscreen viewport, and clean profiles.
  2. Pin/self-host exact benchmark versions. Never compare different Speedometer, JetStream, or MotionMark versions.
  3. Randomize browser order and allow thermal recovery.
  4. Run ten independently restarted samples per browser and test.
  5. Report median, p25–p75, bootstrap 95% confidence interval, raw JSON, hardware, OS, browser, engine, settings, date, and commit.
  6. Initially fail release gates only on a statistically supported >5% latency/score regression or >10% memory regression; tighten after variance is understood.

WKWebView experiment gate

Create a separate, disposable proof of concept after Phase 2. It needs only ephemeral browsing, omnibox, tabs, navigation, content blocking, downloads, and the same local benchmark hooks. Keep it only if it achieves all of the following against optimized Electron on the same machine:

  • At least 25% faster median cold launch to usable omnibox.
  • At least 30% lower private memory at one and ten controlled tabs.
  • Meaningfully lower idle energy and a substantially smaller signed installer.
  • No critical failures in the defined compatibility corpus.
  • A credible security/update plan for macOS releases.

If it fails any hard gate, delete the experiment and continue with Electron. A rendering-core rewrite is out of scope: Minimal wins by reducing browser overhead, not by trying to outstaff Chromium, WebKit, or Gecko.

Recommended page order

  1. Hero with supported-platform badge and honest CTA.
  2. Real product screenshot or launch clip.
  3. Benchmark scorecard with methodology and raw-results link.
  4. Three focused differentiators: low-distraction shell, default blocking, ephemeral sessions.
  5. Privacy and security model, including what is and is not persisted.
  6. Install steps, system requirements, signing/notarization status, checksum, and release notes.
  7. Keyboard shortcuts and footer.

Site quality fixes

  • Preserve the self-contained page and ~9.7 KB gzip baseline.
  • Resize the ~930 KB touch icon to its actual display dimensions.
  • Add explicit :focus-visible rings, a skip link and <main>, stronger small-text contrast, and correct tabs semantics.
  • Make reveal content visible by default and add animation only after a JavaScript capability class is active.
  • Report clipboard failure instead of treating rejection as success.
  • Add CSP, nosniff, referrer policy, compression verification, and immutable caching for versioned assets.
  • Gate releases with five Lighthouse desktop/mobile runs, median reporting, and retained reports; use field Core Web Vitals only after sufficient traffic exists.

8. First implementation slice

  1. Add a failing performance test around a 100k-rule non-match.
  2. Implement label-based suffix lookup without changing blocking semantics.
  3. Add cache metadata and prevent refresh when fresh.
  4. Add startup/navigation marks and a JSON result schema.
  5. Repair ESLint so the release gate actually checks source.
  6. Run the full unit/build/bundle suite and record the new local baseline.
This slice is small enough to review, directly attacks the proven hot path, and creates the evidence needed for every later architecture decision.
